# Interaction Contract

这份协议定义 `auto-diagram` 在整个流程中的固定交互形态。

目标不是“更花”，而是让用户一眼知道：

- 当前走到哪一步
- 哪些内容是回执
- 哪些地方需要自己确认
- 下一步到底要回什么

## 阶段启动标识

进入关键阶段时，统一使用：

- `🎨 auto-diagram - Brainstorm 已激活`
- `🎨 auto-diagram - Diagram Brief 已激活`
- `🎨 auto-diagram - Spec 已激活`
- `🎨 auto-diagram - Backend Routing 已激活`
- `🎨 auto-diagram - Draft Preview 已激活`
- `🎨 auto-diagram - 质量闸门 已激活`
- `🎨 auto-diagram - Delivery 已激活`

不要直接用普通解释段落代替阶段启动提示。

## 固定回执标题

高频回执统一使用这些标题：

- `🧾 已知信息回执`
- `❓ 待确认点`
- `✨ 增强建议`
- `🧭 推荐默认方向`
- `📦 Diagram Brief`
- `🧱 Unified Spec 摘要`
- `🧭 路由命中`
- `🖼️ 草稿图`
- `📐 比例建议`
- `🧠 构图结论`
- `🔍 本轮确认重点`
- `🔁 修改吸收`
- `🛠️ 生成计划`
- `🧩 主题包沉淀`
- `🧪 质量检查`
- `🚦 质量闸门 Q1/5｜结构闸门`
- `🛠️ 质量闸门 Q2/5｜关键修复`
- `🖼️ 质量闸门 Q3/5｜效果预览`
- `🎨 质量闸门 Q4/5｜视觉打磨`
- `✅ 质量闸门 Q5/5｜交付复核`
- `📋 批量修复报告`
- `✅ 当前产出`
- `⚠️ 假设 / 风险`
- `📊 可选导出`

不要同一轮里自己发明很多风格不一的小标题。

## 用户输入协议

### 只补一个事实

如果只需要用户补一个事实，不要做菜单，直接明确提示：

- `👉 请补 1 个信息：这张图主要给谁看？`
- `👉 请确认 1 件事：更偏老板汇报，还是团队执行？`

### 存在明确分叉

如果用户需要在 2-4 个方向里做明确选择，使用菜单：

```text
📍 当前: 已完成第一轮需求锁定
📌 下一步:
[1] 确认推荐方向 - 直接按默认方案进入草稿图
[2] 补充关键信息 - 再补 1-2 个会影响结构的点
[3] 切换图型 - 改成另一种更适合的表达骨架
[0] 暂停 - 先不继续
```

规则：

- `[0]` 只保留给暂停 / 先不继续
- `[1]` 放当前最推荐动作
- 每个选项只表达一个动作
- 风险说明放菜单前，不放进选项正文里

## Mandatory Brainstorm 固定形态

第一轮 brainstorm 必须至少出现这四段：

- `🧾 已知信息回执`
- `❓ 待确认点`
- `✨ 增强建议`
- `🧭 推荐默认方向`

如果第一轮结束时需要用户拍板，默认接一个轻量菜单，而不是开放式让用户“再描述一下”。

如果 brainstorm 阶段给了主题包建议，默认放在：

- `✨ 增强建议`
- 或 `🧭 推荐默认方向`

不要为了主题包再额外发明一套新标题。

## 主题包提示协议

- 推荐主题包时，不要默认枚举全量 pack
- 默认提示：
  - `我们现在有 X 个主题包可选；如果你想看全量，我可以再展开`
- 这里的 `X` 默认通过 `python3 scripts/theme/list-theme-packs.py --count` 获取
- 如果用户给了自定义风格词，就把主题包降级为可选建议，不要强推回预设
- 如果用户给了参考图并要求“按这个风格”，优先走参考图学习路线

## 路由命中固定形态

当图型、双图策略、layout family 或 backend family 已经锁定时，不要把判断结果埋在长段解释里。

推荐格式：

```text
🧭 路由命中: SVG-first 总览图
```

或：

```text
🧭 路由命中: PlantUML 正式图 + SVG 总览图
```

## Diagram Brief 固定形态

进入 intake 之后，至少要有：

- `📦 Diagram Brief`
- `⚠️ 假设 / 风险`

如果图型仍未锁定，再追加：

- `📌 候选图型`
- 菜单式确认

## Draft Preview 固定形态

在 unified spec 和 layout family 已经锁定、但还没进入正式 SVG 或其他重渲染时，至少要有：

- `🖼️ 草稿图`
- `📐 比例建议`
- `🧠 构图结论`
- `🔍 本轮确认重点`
- `⚠️ 假设 / 风险`

`🖼️ 草稿图` 默认要求：

- 直接给出一版低保真线框，不要只用几条分点文字代替草稿
- 草稿外形必须和当前比例一致；如果写的是 `16:9`，草稿本身就要明显是横版宽画幅，不能是竖长长条
- 如果内容过密，优先扩大草稿宽度，或把区块正文降到标题 / 标签级；不要为了塞细节破坏比例
- 当比例和正文细节不可兼得时，先保标题区、分区、主节点、主链路和关键说明卡标题，把细节转移到文字回执区

`📐 比例建议` 默认包含：

- 当前比例：如 `16:9`
- 推荐尺寸：如 `1920x1080`
- 来源：默认值 / skill 推荐 / 用户锁定
- 简短理由：为什么这个比例更适合当前构图

如果用户已经给了比例，直接说明“按用户比例锁定”，不要再假装把选择权丢回给用户。

如果要等用户拍板，默认菜单：

```text
📍 当前: 草稿图已生成，主结构和阅读路径已可见
📌 下一步:
[1] 确认草稿图 - 进入正式渲染
[2] 提修改意见 - 我先吸收修改并重出草稿
[3] 回退结构 - 调整图型 / 分组 / 主叙事
[4] 切换导出比例 - 改画幅后重出草稿
[0] 暂停 - 先不继续
```

规则：

- 用户没有明确确认前，不要开始正式渲染和质量脚本
- 用户提出修改后，先给 `🔁 修改吸收`，再重出一版草稿
- 如果用户指定了比例，草稿图和最终渲染都要沿用这个比例；除非用户同意，不要切换
- 如果去掉比例说明文字后，草稿外形已经看不出当前画幅，先修草稿，不要急着问用户确认
- 如果修改已经影响图型或布局骨架，回到 routing 或 intake，不要硬在当前草稿上缝补

## 质量闸门固定形态

进入正式渲染后的质量阶段时，先按 [../quality/batch-repair-loop.md](../quality/batch-repair-loop.md) 执行批量闸门轮回。

用户可见回执必须使用 `质量闸门 Qx/5｜阶段名` 格式；内部术语只允许出现在命令、脚本参数、JSON 字段或维护文档里。

对外阶段名：

| 内部术语 | 用户可见阶段 |
|---|---|
| hard preflight | `🚦 质量闸门 Q1/5｜结构闸门` |
| hard batch repair | `🛠️ 质量闸门 Q2/5｜关键修复` |
| round preview | `🖼️ 质量闸门 Q3/5｜效果预览` |
| soft polish | `🎨 质量闸门 Q4/5｜视觉打磨` |
| hard guard / final export check | `✅ 质量闸门 Q5/5｜交付复核` |

### Q1/Q2 结构闸门与关键修复

每轮结构闸门必须先运行：

```bash
python3 scripts/quality/run-quality-preflight.py --stage hard <svg-file>
```

规则：

- 同一轮结构闸门要批量收集所有关键结构问题，不要遇到第一个失败就停下来让 Agent 只修一个
- Agent 每轮基于 `📋 批量修复报告` 批量修复，不直接把完整脚本原始日志甩给用户
- 每轮关键修复后，必须运行 `python3 scripts/quality/render-quality-preview.py <svg-file> --stage hard --round <n> --label after-repair`
- 在进入下一轮结构闸门或菜单前，必须展示 `🖼️ 质量闸门 Q3/5｜效果预览`，包含 PNG 图或 SVG / PNG 链接；纯文本 harness 至少给绝对路径
- 关键修复最多自动跑 3 轮
- 第 3 轮后如果仍有关键结构问题，必须给菜单：

```text
🛠️ 质量闸门 Q2/5｜关键修复
状态：已自动修复 3 轮，仍有 X 个关键结构问题
📌 下一步:
[1] 接受当前版本 - 交付 SVG + 关键问题报告，用户自行修复
[2] 继续让 Agent 修复 - 额外再跑一轮批量修复
[0] 暂停 - 先不继续
```

### Q1 结构闸门通过确认

关键结构问题清零后，不要默认直接进入视觉打磨。先给菜单：

给菜单前必须先展示当前 `🖼️ 质量闸门 Q3/5｜效果预览`。如果最近一轮没有生成预览，先运行：

```bash
python3 scripts/quality/render-quality-preview.py <svg-file> --stage hard --round <n> --label hard-clean
```

```text
🚦 质量闸门 Q1/5｜结构闸门通过
状态：关键结构问题已清零，当前版本可以安全导出
📌 下一步:
[1] 进入 Q4 视觉打磨 - 继续优化层级、留白和汇报可读性
[2] 接受当前版本 - 直接导出 SVG / PNG
[0] 暂停 - 先不继续
```

非交互模式下默认选择 `[1]`，继续进入 Q4 视觉打磨。

### Q4 视觉打磨

视觉打磨也走批量逻辑。每轮先运行：

```bash
python3 scripts/quality/run-quality-preflight.py --stage soft <svg-file>
```

规则：

- 同一轮视觉打磨要批量收集可优化项 / 打磨建议，不要逐条打磨逐条重跑
- 每轮视觉打磨后，必须运行 `python3 scripts/quality/render-quality-preview.py <svg-file> --stage soft --round <n> --label after-polish`
- 在进入 Q5 交付复核、下一轮视觉打磨或菜单前，必须展示 `🖼️ 质量闸门 Q3/5｜效果预览`，包含 PNG 图或 SVG / PNG 链接；纯文本 harness 至少给绝对路径
- 每轮视觉修改后，必须运行结构闸门作为修后复检；如果出现关键结构问题，回到 Q2 关键修复
- 视觉打磨最多自动跑 3 轮
- 第 3 轮后如果仍有可优化项 / 打磨建议，必须给菜单：

```text
🎨 质量闸门 Q4/5｜视觉打磨
状态：已自动打磨 3 轮，当前仍有 X 个可优化项 / 打磨建议
📌 下一步:
[1] 接受当前版本 - 直接导出交付
[2] 继续让 Agent 打磨 - 额外再跑一轮视觉打磨
[0] 暂停 - 先不继续
```

### Q5 交付复核

进入最终导出前，用户可见回执使用：

```text
✅ 质量闸门 Q5/5｜交付复核
状态：结构闸门已通过，最近一轮视觉修改已完成复检
下一步：导出 SVG / PNG
```

如果交付复核发现新的关键结构问题，回到 `🛠️ 质量闸门 Q2/5｜关键修复`，不要把内部 guard 日志直接丢给用户。

## 交付回执固定形态

出图完成后，交付回执至少要有：

- `✅ 当前产出`
- `🧠 一句主结论`
- `🗺️ 推荐阅读路径`

如果图较复杂或用户要汇报，再追加：

- `🗣️ 30 秒讲法`
- `🔍 可能被追问的点`

内部后处理约束：

- metadata 状态稳定化和受控状态校验属于内部动作，不作为单独用户回执展示
- 不注入可见水印；不要手写水印，不要让模型在图里额外输出水印文字、logo 或品牌页脚
- 不要对用户说“现在执行稳定化脚本”或类似脚本/process chatter
- 用户可见交付只讲结果，例如“图片已生成并通过质量检查”

## PPTX 追加导出协议

只有在 `.svg` / `.png` 已经生成之后，才允许问用户是否需要 `pptx`。

默认菜单：

```text
📍 当前: 图片已生成并通过质量检查
📌 下一步:
[1] 返回图片 - 直接交付 SVG / PNG
[2] 生成 PPTX - 稳定单页汇报稿（图片版）
[3] 生成可编辑 PPTX - 仅限当前 auto-diagram 受控 SVG
[4] 沉淀为主题包 - 仅当本次风格来自参考图学习且值得复用
[0] 暂不导出 - 先看图再决定
```

规则：

- 用户没有确认前，不要默认导出 `pptx`
- 如果用户一开始就明确要求 `pptx`，可以不再重复提问
- 默认 `pptx` 方案强调稳定交付，不承诺可编辑 shape 级还原
- 只有当用户明确要“可编辑 PPT”时，才允许走可编辑导出
- 可编辑导出只承诺本 skill 自己产出的受控 SVG；第三方 SVG 不在保证范围内
- 受控 SVG 必须已经执行 `scripts/stabilize-svg.cjs` 或 `scripts/finalize-svg.cjs`，确保 metadata 状态封印存在
- 这些稳定化与受控状态要求默认由 skill 静默完成，不需要在菜单前后额外播报脚本执行过程
- `[4]` 只在当前任务确实来自参考图学习、且最终图已经完成后才出现；不要对普通内置主题包任务乱问

## 非交互模式

当 prompt 同时满足以下两个条件时，视为非交互模式（eval / batch / automated runs）：

1. 已预填全部 brainstorm 参数（audience / purpose / core_message / story_axis / style 等）
2. 明确要求"直接出图"或等价指令

非交互模式下：

- brainstorm 阶段自动确认，不弹菜单，直接进入 intake → spec → routing
- 草稿确认阶段自动通过，不弹确认菜单，直接进入正式渲染、质量检查和交付
- 所有需要用户拍板的分叉点，一律选择推荐默认值
- 仍然保留阶段启动标识和回执标题，但跳过等待用户确认的步骤
- PPTX 追加导出菜单不弹出，除非 prompt 中明确要求 PPTX
