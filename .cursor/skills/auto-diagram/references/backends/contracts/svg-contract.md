# SVG Contract

为了让后续脚本可以校验，尽量遵守统一的结构与命名。

## 根节点

默认示例可以使用 `16:9`：

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 1920 1080">
```

但这不是唯一合法画幅。最终 `viewBox` 必须服从 unified spec 里已经锁定的比例：

- 默认 `16:9`：`1920x1080`
- 更适合纵深的 `4:3`：`1600x1200`
- 介于横向与纵向之间的 `3:2`：`1800x1200`
- 矩阵 / 象限 / 辐射型的 `1:1`：`1400x1400`
- 纵向长图 `4:5`：`1200x1500`
- 纵向长图 `9:16`：`1080x1920`

规则：

- 如果用户在草稿阶段指定了比例，最终 SVG 不得静默回退到 `1920x1080`
- 如果草稿阶段已经确认了推荐比例，最终 SVG 的 `viewBox` 必须保持同一比例
- 当内容装不下时，优先在同一比例内重排布局、扩画布尺寸或降低密度；不要先破坏比例一致性

## 收尾稳定化

任何后端只要产出 `.svg`，在继续做校验、导出 `.png`、导出 `.pptx` 或直接交付前，都必须执行：

```bash
node scripts/stabilize-svg.cjs <svg-file>
```

兼容入口 `node scripts/finalize-svg.cjs <svg-file>` 也可以，但目标一致：

- 让 SVG 进入 `auto-diagram` 的受控状态
- 在 `</svg>` 前写入 metadata-only 状态封印
- 不注入可见水印、logo、署名或额外品牌标记
- 避免后续 editable PPTX、结构校验或交付链路拿到“裸 SVG”

额外约束：

- 稳定化脚本只写 metadata 状态，不生成任何可见图形层
- 禁止手写、手工绘制、手工粘贴或通过提示词要求模型输出任何水印
- 不要在主图、页脚、角落、标题区或背景层手工绘制任何额外品牌署名
- 明确禁止 `auto-diagram 生成`、`Generated by auto-diagram`、`Made with auto-diagram`、额外 logo 字样或品牌页脚

## 字体规则

默认字体栈必须优先使用下面这组无衬线字体：

```css
font-family: "PingFang SC", "Microsoft YaHei", "Hiragino Sans GB", "Noto Sans CJK SC", "Noto Sans SC", "Source Han Sans SC", "Segoe UI", "Helvetica Neue", Arial, sans-serif;
```

要求：

- `PingFang SC` 是首选
- `Microsoft YaHei` 是第一回退
- 其余 fallback 保持常见 CJK / Web sans-serif，不要混入 serif
- 除非用户明确要求品牌字或特殊风格，否则标题、正文、说明卡、图例、边标签都沿用同一套 sans-serif 字体栈
- 如果后端无法精确表达整条字体栈，也要选择最接近的 CJK 友好无衬线字体，不要主动切到 Times、Songti、Georgia 一类衬线体

## 用户可见性

- `stabilize-svg.cjs` / `finalize-svg.cjs` 是内部后处理工具，不是用户可见阶段
- 必须执行，但默认静默完成
- 不要在对外文案里写“正在执行稳定化脚本”或类似脚本/process chatter

## Page Chrome

`ad-title`、`ad-subtitle`、`ad-legend` 属于页面级 chrome，不是可以随便压住的装饰文字。

规则：

- 页面主标题、副标题默认属于 `title_zone`
- 页脚 legend / 阅读提示默认属于 `footer_zone`
- `ad-node-box`、`ad-note-box`、`ad-group-box`、`ad-stage-box`、`ad-edge`、`ad-edge-label` 都不得侵入这些 zone
- 如果上方存在摘要卡或老板版备注，它也只能作为 header chrome 的旁侧补充，不能盖住标题块
- 页面级 chrome 必须保留左右 gutter，不得把文字直接顶到页面边缘

## Theme Pack Token Mapping

如果当前任务命中了 `theme pack`，推荐把 pack token 优先映射到一个集中 `<style>` 块，而不是把颜色和字号散落在全图里。

推荐变量族：

- `--ad-page-bg`
- `--ad-surface-bg`
- `--ad-canvas-bg`
- `--ad-grid-stroke`
- `--ad-title-color`
- `--ad-subtitle-color`
- `--ad-text-primary`
- `--ad-text-secondary`
- `--ad-edge-color`
- `--ad-edge-label-color`
- `--ad-node-radius`
- `--ad-group-radius`
- `--ad-stage-radius`

如果要继续做语义角色映射，推荐沿用：

- `--ad-role-frontend-fill` / `--ad-role-frontend-stroke`
- `--ad-role-backend-fill` / `--ad-role-backend-stroke`
- `--ad-role-database-fill` / `--ad-role-database-stroke`
- `--ad-role-cloud-fill` / `--ad-role-cloud-stroke`
- `--ad-role-security-fill` / `--ad-role-security-stroke`
- `--ad-role-external-fill` / `--ad-role-external-stroke`
- `--ad-role-message-bus-fill` / `--ad-role-message-bus-stroke`

规则：

- `theme pack` 负责颜色、字体、间距建议和外围 chrome，不负责节点坐标
- 如果当前任务是自由风格生成，也尽量把结果压回这组 token 家族，便于后续导出和复用
- 为了速度，允许最终 SVG 直接内联具体值；但内置主题包和常驻主题包最好能一一对回对应 token

## PNG 导出兼容性

如果最终还要走 `rsvg-convert` 导出 PNG，必须额外遵守一条兼容规则：

- 不要把 `var(--token)` 直接塞进 `font:` shorthand 里当作最终光栅化输入
- 例如这类写法对浏览器通常没问题，但对 PNG 导出不稳定：
  - `font: 700 34px var(--ad-font-family);`
- 更稳的方式有两种：
  - 直接写显式字体属性：`font-family` / `font-size` / `font-weight`
  - 或在导出前先把 `<style>` 里的 CSS 变量 materialize 成显式值，再交给光栅器
- 颜色、描边、圆角等 token 仍然可以在 authoring 阶段保留变量；但进入 PNG 导出时，最好一并展开成 raster-safe CSS

当前 skill 默认通过：

- `node scripts/svg/materialize-css-vars.cjs <input-svg> <output-svg>`

在 PNG 导出前做一次兼容化，再调用 `rsvg-convert`。

## 节点结构建议

```xml
<g class="ad-node" data-node-id="scheduler" data-pad-x="24" data-pad-top="18" data-pad-bottom="18">
  <rect class="ad-node-box" x="420" y="220" width="220" height="110" rx="16" ry="16"/>
  <text class="ad-node-title" x="530" y="254" text-anchor="middle">Global Scheduler</text>
  <text class="ad-node-body" x="530" y="284" text-anchor="middle">issue warps / waves</text>
</g>
```

要点：

- 每个主节点最好单独成组
- 每个节点必须有 `data-node-id`
- 节点文字默认水平居中
- 使用 `data-pad-x`、`data-pad-top`、`data-pad-bottom` 便于脚本检查
- 如果节点属于某个分区，建议补充 `data-group-id`
- 如果节点应该落在主舞台内，建议补充 `data-stage-id`
- 如果节点在主次层级中承担特定角色，建议补充 `data-role`
- 如果节点处于规则网格中，建议补充 `data-row` 和 `data-col`
- 如果节点属于主链路或辅助链路，建议补充 `data-flow-level`

## 主舞台结构建议

如果图存在一个明确的主舞台、安全区或主工作面，建议显式声明：

```xml
<g class="ad-stage" data-stage-id="main-stage">
  <rect class="ad-stage-box" x="52" y="188" width="1616" height="580" rx="28" ry="28"/>
</g>
```

对应节点建议写成：

```xml
<g class="ad-node" data-node-id="sources" data-stage-id="main-stage" ...>
```

如果图里只有一个 `ad-stage-box`，脚本也会把它当作默认主舞台检查节点越界。

## 分组结构建议

如果图中存在明确分区、阶段区、泳道或大容器，建议显式声明分组：

```xml
<g class="ad-group" data-group-id="data-production">
  <rect class="ad-group-box" x="72" y="236" width="490" height="482" rx="24" ry="24"/>
  <text class="ad-group-title" x="100" y="264">DATA PRODUCTION</text>
</g>
```

对应节点建议写成：

```xml
<g class="ad-node" data-node-id="ingest" data-group-id="data-production" data-pad-x="24" data-pad-top="18" data-pad-bottom="18">
```

这样脚本才能检查“节点有没有溢出所属分组”。

说明卡、摘要卡、侧注卡如果用了 `ad-note-box`，也会参与同样的碰撞、边界和安全 gutter 校验；不要把它们当作“可以压住主图的浮层”。

## 最小推荐尺寸辅助

`SVG-first` 现在默认有一层“最小推荐砖块尺寸”辅助，用来避免文字勉强塞进旧砖块后出现贴边、越界、上下失衡。

推荐做法：

- 任意带边框的主节点、说明卡、chip、mini card，优先显式写成 `ad-node` 并补 `data-pad-x`、`data-pad-top`、`data-pad-bottom`
- 即使是很小的 chip，也不要只画一个 `rect + text` 后就假设它天然能装下文案
- 如果只是临时小 chip，质检脚本也会把简单的 `rect + text` 组合当成隐式容器做推荐尺寸计算，但这只是兜底，不是首选规范
- 在改文案、改字号、改语言版本后，建议主动运行 `python3 scripts/quality/check-svg-node-padding.py --recommend <svg-file>` 看每个容器的当前尺寸和最小推荐尺寸
- 当推荐尺寸已经大于当前砖块时，应优先扩砖块，而不是继续下压文字基线或牺牲 padding
- 正式导出链路现在会先跑一遍 `python3 scripts/svg/auto-fit-svg-text.py <svg-file>`，优先尝试正文折行、小幅缩字号、必要时安全扩砖块并重新居中；但这只是收口辅助，不代表可以跳过合理的容器尺寸设计

## 边标签安全区建议

- `ad-edge-label` 不得进入分组标题区
- 边标签默认放在分组标题下方、节点外部通道内
- 如果边与边之间的横向通道太窄，优先把标签上提到通道上沿，而不是让文字吃进节点边缘
- `ad-edge-label` 之间也要保留可读间距；不要把多段文案堆在同一条视觉带里
- `ad-edge-label` 与节点/说明卡之间默认保留至少约 `8px` 的安全距离
- `ad-edge-label` 与箭头端点之间默认保留至少约 `14px` 的安全距离
- 如果标签会压到标题区，优先改线或改标签位置，不要硬贴

任何有边框的说明卡、摘要卡、侧注卡，也建议复用同样的容器方式：

```xml
<g class="ad-node" data-node-id="summary-card" data-pad-x="28" data-pad-top="20" data-pad-bottom="20">
  <rect class="ad-note-box" x="1600" y="80" width="360" height="120" rx="24"/>
  <text class="ad-note-title" x="1780" y="118" text-anchor="middle">一句主结论</text>
  <text class="ad-note-body" x="1780" y="150" text-anchor="middle">
    <tspan x="1780" dy="0">第一行</tspan>
    <tspan x="1780" dy="18">第二行</tspan>
  </text>
</g>
```

## 文本规则

- 标题、正文、副砖块都要位于节点内部安全区
- 标题和正文之间保留稳定节奏，不要贴得太近
- 如果正文超过两行，优先增高节点或缩短文案，不要挤压 padding
- 如果标题或正文变长，优先加宽节点；如果行数变多，优先加高节点。不要只保持原砖块尺寸再把文字硬往下压
- 如果脚本给出的最小推荐尺寸已经超过当前砖块，说明容器尺寸该变了；不要继续靠手调 `y` 值硬塞
- 带边框的正文默认要主动折行；SVG 不会自动换行，不能把长句直接写成单行文本赌运气
- 对正文类文本，长句默认应显式使用 `tspan` 或换行分段；不要把整段解释写成一个 `<text>` 单行节点
- 如果 theme pack 或 font family 切换后文字突然变宽，允许导出前的 auto-fit pass 做补折行、小幅缩字号，以及在不吞边线、不撞相邻容器、不越出母容器时的小范围安全扩砖块，但不应把它当成替代布局设计的主要手段
- 文字块在砖块内部要保持左右留白和上下留白的平衡；不要出现“总高度勉强放得下，但最后一行贴底或越底”的情况
- `30秒讲法`、`推荐阅读路径`、`老板版备注` 这类讲稿型文字默认不属于主图文本层
- `1/2/3/4` 这类序号徽标默认不画；需要序号时优先考虑把顺序藏在布局里，而不是额外加圆点

## 箭头规则

- 箭头用 `<defs>` + `<marker>`
- 默认箭头头部要小且克制
- 多条边之间至少保留可见间距
- 边标签配背景底片，避免压在主图上看不清
- 连线默认优先走节点外部通道，不得横穿主砖块
- 进入或离开节点时，要从边缘锚点出发，不要从砖块中心直接起线
- 如果边很多，先增加留白、分层或改骨架，再画线；不要靠覆盖节点内容换连通性
- 对复杂长反馈线、例外线、控制线，可以通过颜色分层增强区分，不必强求完全靠多次拐弯

### `under-node` 箭头例外

当复杂长箭头已经把绕线成本拉得过高时，允许极小范围使用“节点下层箭头”：

```xml
<path
  class="ad-edge ad-edge-underlay"
  data-edge-channel="feedback"
  data-edge-occlusion="under-node"
  d="M..."
/>
```

规则：

- 只有 `ad-edge` 路径可以使用 `data-edge-occlusion="under-node"`
- `under-node` 只允许节点砖块遮挡箭头主干；文字、边标签、说明卡、摘要卡、分组标题区都不得被遮挡
- `under-node` 适合反馈线、控制线、例外线，不适合主路径主干
- `under-node` 箭头仍然必须从清晰锚点进入/离开节点；允许被遮挡的是中间长段，不是整条线都可以乱穿
- 这类边应优先使用更明确的颜色通道，而不是继续堆拐弯；推荐至少与默认主链边形成肉眼可辨的颜色差
- 如果要实现“被节点遮住”的视觉效果，`under-node` 边应当在 SVG 中绘制在相关节点之前，让节点填充层覆盖它
- 需要可直接照着落图层和 few-shot 时，继续看 [svg-edge-occlusion-patterns.md](svg-edge-occlusion-patterns.md)

推荐默认箭头头部：

```xml
<marker id="ad-arrow" markerUnits="userSpaceOnUse" markerWidth="8" markerHeight="8" refX="7" refY="4" orient="auto">
  <path d="M0,0 L8,4 L0,8 z"/>
</marker>
```
